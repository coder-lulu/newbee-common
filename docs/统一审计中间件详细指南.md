# 统一审计中间件详细指南

## 更新说明
- 2024-11-24：全面校准文档内容，与 `common/middleware/audit` 当前实现一致，补充异步队列、真实 IP 解析、资源命名与元数据策略等细节。

## 1. 概览
统一审计中间件 `AuditPlugin` 负责在认证成功后（优先级 12）立即拦截请求，记录关键审计字段并通过统一写入器持久化。当前实现的核心能力如下：
- **请求/响应采样**：按 `maxBodySize` 限制捕获请求体与响应体，并经 `SensitiveDataFilter` 自动脱敏。
- **资源命名缓存**：调用 `ApiResourceProvider`，使用 `sync.Map` 保存 `METHOD:PATH` → 名称，缓存命中避免反复拉取。
- **操作类型映射**：`mapMethodToOperationType` 将 `GET/HEAD/OPTIONS` 归类为 `READ`，其余 HTTP 动词按 CRUD 语义收敛，保证审计枚举稳定。
- **元数据补全**：统一写入 `request_id`、`trace_id`、`client_ip`、`username` 等上下文信息，便于后续分析。
- **异步可靠写入**：`AsyncAuditQueue` 提供多协程消费、失败重试与 `/tmp/audit_dead_letter.log` 死信降级，优雅处理写入压力或 RPC 故障。
- **真实 IP 解析**：根据 `realIpHeader`（例如 `X-Forwarded-For`）提取第一个可信 IP，回退到 `RemoteAddr` 主机段。
- **写入器多态**：支持 `rpc`（默认）、`custom`、`db` 类型。Core 服务通过 `HighPerformanceCoreAuditWriter` 防止自循环，其余服务默认走 RPC。

## 2. 组件结构
```go
// 精简后的插件结构，来自 common/middleware/audit/plugin.go
 type AuditPlugin struct {
     core            *framework.CoreServices
     config          *framework.AuditConfig
     asyncQueue      *AsyncAuditQueue
     resourceCache   *sync.Map
     sensitiveFilter *SensitiveDataFilter
     logger          *logging.MiddlewareLogger

     builtinWriter framework.AuditWriter
     builtinConfig *framework.AuditConfig
     rpcProvider   AuditSvcProvider
     customWriter  framework.AuditWriter
 }
```

### 2.1 AsyncAuditQueue
- 使用 `context.WithCancel` 管理生命周期，`Shutdown()` 会关闭 channel、广播取消并等待所有 worker 退出。
- 每名 worker 从队列中取出 `AuditLogData` 后，基于租户/用户信息重建上下文，再写入 RPC；失败时指数退避重试 3 次。
- 队列满或 RPC 持续失败时，将完整日志落盘 `/tmp/audit_dead_letter.log`，格式为单行 JSON，便于后续补偿。

### 2.2 SensitiveDataFilter
- 预置身份证、手机号、口令等字段正则，写入前对请求体与响应体执行逐字段脱敏。
- 支持业务在 `AuditLogData.Metadata` 中追加标识，用于标记是否已做额外清洗。

### 2.3 写入器与提供者
- `AuditSvcProvider` 仅需暴露 `GetCoreRpcClient()`；对于 Core 服务，会返回具备降级能力的客户端。
- `BuiltinAuditWriter` 优先断言客户端实现了 `AuditRPCClient`，未实现时退回反射调用以兼容旧版。
- `WriterType=custom` 时跳过内置写入器，使用集成时传入的 `AuditWriter`；`WriterType=db` 预留给直写数据库的实现。

## 3. 配置项
`framework.AuditConfig` 支持以下字段：

| 字段名 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| `enabled` | bool | `false` | 是否启用审计插件 |
| `skipPaths` | []string | - | 以路径前缀匹配跳过审计的 API |
| `writerType` | string | `rpc` | `rpc` / `db` / `custom` |
| `maxBodySize` | int64 | 1_048_576 | 请求/响应体截断阈值（字节） |
| `asyncEnabled` | bool | `true` | 是否启用异步队列 |
| `asyncWorkers` | int | `3` | 异步 worker 数量 |
| `asyncBufferSize` | int | `1000` | 队列容量 |
| `captureResponseBody` | bool | `true` | 是否持久化响应体 |
| `realIpHeader` | string | 空 | 真实 IP 头，示例 `X-Forwarded-For` |

典型配置示例：
```yaml
middleware:
  audit:
    enabled: true
    realIpHeader: X-Forwarded-For
    captureResponseBody: true
    asyncWorkers: 6
    asyncBufferSize: 2000
    skipPaths:
      - /health
      - /metrics
      - /captcha
```

## 4. 请求处理流程
1. **跳过判断**：`shouldSkip` 按前缀比对 `skipPaths`，满足时直接透传。
2. **请求体捕获**：`captureRequestBody` 兼容可重复读取流，超过 `maxBodySize` 自动截断，并交给 `SensitiveDataFilter`。
3. **响应封装**：将 `http.ResponseWriter` 包装为 `responseWriterWrapper`，记录状态码与限定长度的响应内容。
4. **上下文取值**：利用 `ContextManager` 获取 `tenant_id`、`user_id`、`username`、`request_id`、`trace_id` 等信息。
5. **资源命名**：先查 `resourceCache`，未命中则调用 `ApiResourceProvider`；失败时回退到 `METHOD normalizedPath` 组合。
6. **客户端 IP**：`resolveClientIP` 会拆分 `realIpHeader`，自动忽略空值和 `unknown`。
7. **队列写入**：若开启异步，调用 `AsyncAuditQueue.Enqueue`；否则直接执行 `builtinWriter.WriteAuditLog`。
8. **失败处理**：当队列关闭/满或 RPC 返回失败时记录错误并写入死信文件，保证主请求不被阻断。

## 5. 集成步骤
```go
result, err := integration.Setup(&integration.Config{
    Redis:               svcCtx.Redis,
    JWTSecret:           jwtSecret,
    Mode:                integration.Production,
    ApiResourceProvider: svcCtx.NewApiResourceProvider(),
    AuditWriter:         audit.NewBuiltinAuditWriter(svcCtx), // Core 服务会改为 custom
    TenantInfoProvider:  svcCtx.NewTenantProvider(),
    RbacProvider:        svcCtx, // 可选
    Middleware:          &svcCtx.Config.Middleware,
})
if err != nil {
    logx.Fatalf("middleware setup failed: %v", err)
}

svcCtx.ContextManager = result.ContextManager
svcCtx.ManagedMiddlewareChain = result.Middlewares
svcCtx.IntegrationResult = result
```
- Core 服务需将 `writerType` 强制设为 `custom` 并传入 `HighPerformanceCoreAuditWriter`，避免 RPC 自调用。
- 其余服务复用 `audit.NewBuiltinAuditWriter`，确保 `GetCoreRpcClient()` 返回可用的 Core RPC 客户端。

## 6. 扩展实践
- **自定义资源命名**：实现 `framework.ApiResourceProvider`（例如缓存 Core RPC 查询结果的 provider），并在 `integration.Config` 注入。
- **直接写库**：若需要绕过 Core RPC，可实现 `AuditWriter` 将日志落至本地表，再透过 ETL 汇总。
- **动态跳过路径**：结合配置中心更新 `skipPaths` 后重启或热更新中间件链，避免高频接口写审计。
- **响应捕获策略**：对文件下载、流式接口设置 `captureResponseBody: false`，防止大响应写入日志。

## 7. 故障排查
| 现象 | 可能原因 | 建议处理 |
|------|----------|----------|
| 审计日志缺失 | 队列已关闭或写入失败落入死信 | 检查 `/tmp/audit_dead_letter.log` 并排查 Core RPC 健康度 |
| ResourceName 为空 | `ApiResourceProvider` 未返回有效值 | 查看服务 Provider 实现或缓存过期逻辑 |
| IP 为 `127.0.0.1` | 未配置 `realIpHeader` 或代理未透传 | 在配置中声明可信头，并确保代理传递原始 IP |
| OPTIONS/HEAD 未生成 | 旧版本写入器缺陷 | 当前版本已统一映射为 `READ`，确认服务依赖已更新 |
| 队列爆满报警 | `asyncBufferSize` 偏小或写入耗时长 | 调整 worker/缓冲区，并监控 Core RPC 延迟 |

## 8. 验证建议
- 针对 `GET/POST/PUT/DELETE/HEAD/OPTIONS` 分别发起请求，确认 `operationType` 各自映射正确。
- 关闭 Core RPC，观察死信文件是否产生且主请求不报错。
- 人为写入包含敏感字段的请求/响应体，确认数据库中的内容已被脱敏。
- 修改 `realIpHeader`，通过代理注入多段 IP，验证解析顺序与回退策略。

以上内容覆盖了 AuditPlugin 在当前版本中的全部关键行为，可据此指导服务接入、调优与排障。
